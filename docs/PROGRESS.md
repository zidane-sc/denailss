## Current Phase

Epics 1, 2, 3, 4 (CRM), 5 (Gallery Management), 6 (Promotion admin), 7 (Finance), and 8 (Analytics) are implemented. The frontend-first phase is complete enough to begin backend wiring. A first backend vertical slice now exists: Drizzle schema + generated Supabase migration, shared API helpers, catalog/availability routes, booking create/list/detail/update routes, server-side catalog validation and pricing, transactional customer/appointment persistence, and frontend booking/backoffice adapters. Google OAuth, SSR session refresh, customer/owner route guards, Auth profile linkage, and RLS policies are now implemented and migrated to Supabase. Authenticated booking ownership is now enforced in the API, guest booking remains supported, and the customer dashboard, booking history/detail, profile, and portal header read persistent Supabase-backed data. **All domains are now Supabase-persisted** — gallery + gallery_images, services, promotions (real quota enforcement), reviews, customer_favorites, settings, CRM (customers + customer_notes + preferences), finance expenses, analytics/finance derivations from real appointments, the availability config (weekly template, overrides, blocked times, vacations, booking rules), and the deposit config (enabled/type/value/payment methods/notes). The booking slot engine, server-side rules, and deposit calculation all read DB config. No `*.mock.ts` config seams remain — the only remaining mocks are dev fixtures (backoffice appointment seed, instagram posts, CRM/finance seed data no longer imported).

**Remaining domain migration is not complete.** Upload endpoints now have server-side in-memory rate limiting: owner catalog uploads are limited to 20/hour per IP+owner, and deposit proof uploads to 5/hour per IP. **In-memory rate limiting is the accepted approach** (per the owner decision) — a distributed limiter (Redis/Upstash) is not planned unless the app moves to multi-instance production. Supabase Storage buckets/policies are live, catalog upload requests now use Storage references, settings logo uploads use the Storage bucket, and deposit proof uploads persist to the private bucket with owner signed-URL display and lifecycle cleanup (abandoned uploads tracked + removed, replaced/removed proofs deleted, rejected proofs deleted and cleared). **All domains persist to Postgres** — gallery, services, settings, promotions, reviews, favorites, CRM (customers + notes + preferences), finance expenses, the availability config (weekly template, overrides, blocked times, vacations, booking rules), and the deposit config; income/analytics derive from real DB appointments and the slot engine/server-side rules/deposit calculation read DB config. The **real-data-only** decision means backoffice CRM/finance/analytics start from real bookings only — no fictional history is seeded. The service-role key must be configured in deployment for server-side uploads. Public booking fails explicitly when the API/database is unavailable instead of creating a misleading session-only booking. The approved Google accounts must be promoted with `supabase/OWNER_SETUP.sql` before `/backoffice` is accessible; the SQL supports two owner UUIDs. Auth/RLS SQL is hand-authored under `supabase/migrations/0001_auth_rls.sql`, Storage under `0003_storage.sql`, the existing-account profile backfill under `0002_backfill_auth_profiles.sql`, the gallery-images seed backfill under `0004_gallery_images_backfill.sql`, the settings table/seed under `0005_settings.sql`, the deposit-upload tracking table under `0006_deposit_uploads.sql`, promotions under `0007_promotions.sql`, reviews under `0008_reviews.sql`, favorites under `0009_favorites.sql`, the appointments `promo_code` column under `0010_appointments_promo_code.sql`, the CRM/expenses persistence under `0011_crm.sql`, the availability config (vacations + booking rules) under `0012_availability.sql`, and the deposit config under `0013_deposit_config.sql`.

### Booking flow (`src/features/booking/`)
- **Tier-aware booking pricing** — customers now pick the difficulty tier (Simple/Complex) for tiered services right in the service step: an inline tier selector appears when a tiered service (Fake Nail, Nail Art) is selected. The subtotal, total, duration (slot availability), deposit, summary, and confirmation all use the chosen tier's price/duration. The tier label is stored on the appointment (`AppointmentService.tierLabel`) and surfaces in the booking summary, confirmation, and backoffice service-name labels (`serviceNamesLabel` renders "Nama (Tier)"). Selection lives in `BookingSelections.tierByServiceSlug`; flat services keep a single price and show no picker.
- Dynamic step list built from the selected services:
  - **Desain** appears only when the selection includes nail-art, fake-nail, or gel-extension (skipped for manicure/pedicure/removal-only bookings). The step lists the **live admin catalog** (via `useLiveGalleryDesigns`) — no service filtering, since any design can be applied to any eligible service (including press-on).
  - **Pengambilan** (fulfillment) appears when fake-nail is selected (even alongside other services); otherwise Tanggal/Waktu are used.
  - **Promo** is always present for every service combination; **Deposit** only when the selected service requires it.
  - Step index/max-reached are clamped for rendering when the step list changes (services toggled) so navigation never lands out of range.
- **Design and Promo steps are skippable** — `canProceed` defaults to `true` for both, so a customer can leave the design unselected and/or skip the promo code (both optional).
- **Confirmation requires a generated booking code** — the "Selesai" screen renders only once `bookingCode` is set, which happens in `goNext` when leaving the second-to-last step (format `DNL-YYYYMMDD-NNNN`).
- **Availability Engine** (`logic/availability.ts`) is real logic, not fake states: weekly template + per-date overrides + vacation ranges + blocked times + booking rules (window/notice/max-per-day/buffer), computed against seeded mock appointments (`data/appointments.mock.ts`). Produces per-day status (available/limited/full/closed/past/outside-window) and per-slot grouped Pagi/Siang/Malam availability.
- Pricing/discount/deposit math in `logic/pricing.ts`, validated against mock promotions with real rule checks (date window, min spend, applicable services, usage limit, max discount cap).
- Customer info step uses `react-hook-form` + `zod` (`validators/booking.schema.ts`).
- Booking selections live in `booking-flow.tsx` until submission; completed bookings are persisted through `POST /api/v1/bookings` and are no longer mirrored into a session-only fallback when the API fails.
- **Slot-conflict validation (overlap-aware)** — `createBooking` and the backoffice reschedule path check the requested slot against existing appointments with the configured buffer on both sides: an existing booking blocks `[start - buffer, end + buffer]` and a new booking conflicts if it intersects. The daily capacity cap (`maxBookingsPerDay`) counts every occupied slot for the day (statuses `confirmed`/`waiting_verification`/`pending_deposit`/`pending`). Both the daily cap and the per-slot overlap reject with a `409 CONFLICT` inside the booking transaction.
- Deposit upload sends the proof file to a private Supabase Storage bucket and persists the `storage:deposit-proofs/...` reference in the appointment. The UI still shows a local preview; owner verification displays a signed URL from the private bucket. **Deposit-proof lifecycle cleanup is implemented**: uploads are tracked in `deposit_uploads` until attached to an appointment, the booking form deletes a proof when it's replaced or removed before submit (`DELETE /api/v1/bookings/deposit-proof/delete`), submitting a booking forgets the tracking row, and rejecting a deposit deletes the storage object + clears the reference on the appointment. `cleanupAbandonedDepositUploads()` provides a best-effort sweep of uploads never attached (24h retention).
