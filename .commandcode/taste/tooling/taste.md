# Tooling

- Prefers BrowserAct (browser-act-cli via uv) for browser automation tasks: browsing, clicking, filling forms, handling login flows, solving CAPTCHAs, bypassing bot detection, and extracting structured data from websites. Explicitly directs the assistant to use it when present (e.g., "use the browseract" to fetch Instagram images). Confidence: 0.9

- Uses Command Code's skills system and is open to installing established third-party skill sets (e.g., obra/superpowers) globally into `~/.commandcode/skills` so they're available across all projects, not just one. Confidence: 0.6

- Runs zsh as their shell (nvm loaded via `.zshrc`); when diagnosing shell/PATH issues, expects the assistant to account for zsh configs and behavior. Confidence: 0.9

- Expects dependency installation problems to be diagnosed from the actual lockfile/node_modules state and repaired explicitly, then verified with the real project checks rather than assumed fixed from an npm success message. Confidence: 0.8

- Directs the assistant to use specific Command Code skills for the work at hand (e.g., "use the skill design" for UI work) and expects the skill's process — activating it, reading its references, and following its rules — to be followed rather than ad-hoc implementation. Confidence: 0.7

- Uses browser-act CLI for live browser verification: loads the skill workflow, opens a browser session, screenshots the actual page, and evaluates JS in the DOM to measure rendered geometry (getBoundingClientRect) rather than trusting guesswork. Confidence: 0.6

- When configuring project environment variables, prefers them written directly to the repository-root `.env` file rather than only being shown as instructions or placed in `.env.local`. Confidence: 0.8

- Expects hand-written SQL migrations to be idempotent/re-runnable against the live database: after a migration re-run failed on non-idempotent `CREATE POLICY` statements, the fix was adding `DROP POLICY IF EXISTS` guards before each policy (and `CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS` elsewhere) so re-applying the file is safe — this was accepted without complaint. Confidence: 0.5

- Approves removing dead/unused dependencies to keep the dependency tree lean — when the assistant flagged `date-fns` as installed-but-never-imported and offered to remove it, replied tersely "yeah remove it", expecting the removal to be completed (manifest + lockfile) and verified, not just described. Confidence: 0.6

- Approves pinning the project's Node version via `.nvmrc` for reproducible installs — greenlit adding `.nvmrc` (24.11.1) after the default nvm Node version broke devDependency installs and a transitive dep required Node >=24. Confidence: 0.55

- When an OAuth login redirect misbehaves (e.g., backoffice login redirecting to localhost:3000 after login in production), the source of truth is Supabase's server-side Auth URL Configuration (Site URL / Redirect URLs) and the OAuth provider's authorized redirect URIs — not the app's env vars or code, which may not read `NEXT_PUBLIC_SITE_URL` at all; expects the diagnosis to verify what the code actually reads (e.g., `window.location.origin`, `new URL(..., request.url)`) and point the fix at the dashboard setting. Confidence: 0.6
- Migration execution in this project: migrations are hand-written SQL under `supabase/migrations/` — the Drizzle journal only tracks `0000`, so `drizzle-kit migrate` runs successfully but only applies/re-applies that one journaled migration and silently skips the hand-authored ones — and are applied directly to the live database via `psql` with `DATABASE_URL` — stripping CLI-only `--> statement-breakpoint` markers, wrapping in a transaction with `ON_ERROR_STOP=1`, and verifying schema state (columns/tables/policies) before and after applying to avoid double-apply. Fresh confirmation: for the `maps_url` settings column the assistant confirmed the remote DB was missing the column (no Supabase project-ref linked), applied the `ADD COLUMN IF NOT EXISTS` directly through the app's `DATABASE_URL` connection, and re-verified the settings API afterward. Fresh confirmation: for a bare "run the migration" instruction the assistant ran `drizzle-kit migrate` (no-op for the hand-authored 0001–0022), then confirmed the migrations were already applied by verifying each migration's artifact (tables/columns) in the DB and reported nothing pending — the established practice is trusting actual schema state over the journal's bookkeeping. Fresh confirmation: on a second bare "run the migration," the assistant again found the drizzle journal only tracks 0000 and verified all 22 hand-authored migrations applied by auditing each file's expected artifact (tables, columns, seed rows) directly in the DB — concluding everything was already live and nothing pending. Fresh confirmation: for "run the seed," the supabase CLI was not installed, so the idempotent backfill migration (0024) was applied directly via `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f <file>`, after first confirming via SELECT that the target columns existed but were all empty and that no migration-tracking table existed — then re-verified the populated row afterward before moving on to the code fix. Fresh confirmation: a runtime 500 on POST /contact-messages traced to schema drift — the drizzle schema/service inserts `instagram`, but migration 0023 was never applied to the remote DB; the assistant audited each migration's expected artifacts against the remote, applied the missing idempotent migration via psql, and re-verified with a real POST (201) and test-row cleanup. Confidence: 0.9

- Prefers bulk content seeding to be script-driven rather than a wall of static SQL rows: for the 181-post Instagram portfolio the user asked for a seeding script ("create script to seed the data gallery? 181 data? btw upload the image to supabase storage") that uploads the images to the Supabase Storage bucket and inserts gallery rows, and had the old 20-row `gallery` seed removed from `supabase/seed.sql` so each content set lives in exactly one seeding path. Expects such seed scripts to be idempotent (storage upsert, ON CONFLICT, child-row reconcile) and exposed as an npm script. Confidence: 0.6

- Performance work is driven by hard evidence (file sizes, row counts, payload composition) rather than user guesses: the user's "it's the images" hypothesis was checked against measured image sizes and traced load paths (RSC payloads, provider fetches, cache headers) before being accepted or rejected — conclusions like "the gallery images are fine; the weight is the uncached data fetches" were backed by numbers (181 designs, 618 image refs, ~200KB+ JSON per load). Confidence: 0.6

- Wants web-performance best practices applied comprehensively when requested, especially for images ("implement the best practice for the website please especially image - compress (?) - lazy load"): every image that can be optimized goes through `next/image` — including previously raw `<img>` thumbnails in admin/backoffice views — with AVIF/WebP formats and explicit device/image sizes configured in `next.config.ts`, proper `sizes` values per image, built-in lazy loading, and oversized local source JPEGs compressed with sharp (resized to a sensible long edge for the display context, re-encoded mozjpeg) rather than shipping full-res originals; only truly unoptimizable images (signed storage URLs) stay as raw `<img>` with `loading="lazy"` + `decoding="async"`. Fresh confirmation: pasted Next.js browser warnings for `fill` Images missing the `sizes` prop and the assistant added an explicit `sizes` value per image (24px avatars → `1.5rem`) and swept the whole codebase to confirm no other `fill` Image lacked `sizes` — every `fill` image must carry an explicit `sizes` value. Confidence: 0.85
- Prefers compressing bundled static images at the source (resize to a sensible long edge for the display size, mozjpeg re-encode) rather than relying on the runtime optimizer to shrink them on first request — shipped 2480px/629KB and 452KB source files down 53-90% with a throwaway sharp script, keeping the compressed result in place, and verified with typecheck/lint/build. Confidence: 0.6

- Verifies that seed scripts actually populate every schema field from real data — including derived/display values (e.g., asked "do we already set it in seed?" to confirm the gallery seed derives `aspect` from the actual cover image dimensions) — so a field is never left empty/null by the seeding path.
